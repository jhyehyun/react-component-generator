# commit

변경사항을 읽고, 리뷰하기 좋은 단위로 나눠서, 한국어 컨벤션 메시지로 커밋한다.
사용자가 커밋을 요청한 것 자체가 승인이므로, 별도 확인 질문 없이 분류부터 커밋까지 한 번에 진행한다.

## 절차

### 1. 변경사항 분석

먼저 저장소 상태를 확인한다. `git rev-parse --is-inside-work-tree`가 실패하면 git 저장소가 아니라는 뜻이므로, 커밋할 수 없다고 알리고 `git init`을 할지 사용자에게 묻는다(임의로 초기화하지 않는다).

그다음 아래를 실행해 무엇이 바뀌었는지 파악한다.

- `git status --short` : 수정/추가/삭제/untracked 파일 전체 목록
- `git diff` 와 `git diff --staged` : 실제 변경 내용
- `git log --oneline -10` : 이 저장소의 기존 메시지 스타일 확인

untracked 파일은 `git diff`에 나오지 않으므로 내용을 직접 읽어서 무엇인지 파악한다. diff가 너무 크면 `--stat`으로 윤곽을 잡고 핵심 파일만 자세히 본다.

변경이 하나도 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.

### 2. 논리적 단위로 분류

변경을 "하나의 이유로 설명되는 묶음"으로 나눈다. 한 커밋은 한 가지 일만 해야 나중에 `git revert`나 리뷰가 쉽다.

- 기능 추가, 버그 수정, 리팩터링, 설정/의존성 변경이 섞여 있으면 따로 나눈다.
- 테스트는 대응하는 코드와 같은 커밋에 넣는다.
- 한 파일 안에서 서로 다른 목적의 변경이 섞여 있으면 `git add -p`로 나눌 수 있지만, 대화형 모드는 이 환경에서 지원되지 않으므로 그 경우엔 한 커밋으로 묶고 이유를 알린다.
- 변경이 작고 한 가지 목적이면 커밋 하나로 충분하다. 억지로 쪼개지 않는다.

민감해 보이는 파일(`.env`, 키, 자격 증명, `node_modules`, 빌드 산출물, 대용량 바이너리)은 커밋 후보에서 빼고 사용자에게 알린다. 이미 `.gitignore`에 있어야 하는 것들이다.

### 3. 커밋 메시지 작성

형식:

```
<type>: <한국어 요약>

<필요할 때만: 무엇을 왜 바꿨는지 본문>
```

type은 다음 중 고른다.

| type | 용도 |
| --- | --- |
| feat | 사용자에게 보이는 새 기능, UI 추가 |
| fix | 버그 수정 |
| refactor | 동작은 그대로인 구조 개선 |
| chore | 설정, 의존성, 빌드, 문서 등 코드 동작과 무관한 작업 |

위 네 가지로 애매하면 가장 가까운 것을 쓰고, 저장소 기존 로그가 `docs:`, `test:`, `style:` 같은 다른 type을 이미 쓰고 있다면 그 관례를 따른다.

작성 원칙:
- 요약은 한 줄, 가능하면 50자 안팎. 마침표는 붙이지 않는다.
- "무엇을 했는지"가 아니라 "무엇이 달라졌는지"가 드러나게 쓴다. 예: `feat: 프롬프트 입력창에 예시 선택 기능 추가`
- 요약만으로 이유가 전달되지 않을 때만 본문을 쓴다. 본문은 diff를 다시 설명하지 말고 왜 필요했는지를 쓴다.
- 시스템 컨텍스트에 커밋 attribution 줄(예: `Co-Authored-By: ...`)이 지정돼 있으면 메시지 끝에 빈 줄을 두고 그대로 붙인다. 사용자나 CLAUDE.md가 다르게 지시했으면 그쪽이 우선이다.

### 4. 커밋 실행

승인 질문 없이 바로 커밋한다. 대신 어떤 커밋을 만들었는지는 마지막에 반드시 보고해서, 사용자가 결과를 확인하고 필요하면 되돌릴 수 있게 한다.

실행 시:
- 커밋마다 파일을 이름으로 명시해서 `git add <파일들>` 한다. `git add -A`/`git add .`는 계획에 없는 파일(비밀 키, 산출물)을 쓸어 담을 수 있어서 쓰지 않는다.
- 메시지는 여러 줄일 수 있으므로 `-m`을 여러 번 쓰거나 heredoc을 사용한다.
- 훅(pre-commit 등)이 실패하면 `--no-verify`로 우회하지 말고, 실패 원인을 보여주고 고친 뒤 새 커밋으로 만든다. 이미 만든 커밋을 `--amend`로 덮어쓰지 않는다.
- 모든 커밋이 끝나면 `git log --oneline -n <커밋 수>`와 커밋별 포함 파일을 보고한다.

푸시는 요청받지 않았다면 하지 않는다. 커밋만 하고 "푸시는 하지 않았다"고 한 줄 알려준다.
