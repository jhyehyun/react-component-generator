# TDD Rule

**이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 일부만 적용하지 않는다.

## 1. 적용 기준

### TDD를 반드시 적용하는 대상

- 비즈니스 로직 (조건 분기, 계산, 상태 전이, 데이터 변환)
- API (핸들러, 요청/응답 처리, 에러 매핑)
- 유틸리티 / 순수 함수
- 버그 수정 (**버그를 재현하는 실패 테스트를 먼저 작성**한다)

### TDD가 불필요한 대상

- 타입 정의 (`interface`, `type`)
- 설정 파일 (`package.json`, `tsconfig`, `vite.config`, eslint 등)
- 순수 UI (로직 없는 마크업, 스타일, 레이아웃)
- SQL (스키마, 마이그레이션, 단순 쿼리)

경계가 애매하면 **로직이 있으면 적용**한다.

## 2. RED-GREEN-REFACTOR 사이클

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 검증하지 않는다.
- 테스트 이름은 기대 동작을 서술한다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 RED가 아니다.
- **실패 이유가 "기능 미구현"이어야 한다.** 오타, import 오류, 문법 오류, 잘못된 셋업으로 인한 실패는 RED가 아니므로 테스트를 고쳐 다시 실행한다.

### GREEN: 최소 구현

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. **YAGNI** — 요구되지 않은 기능, 일반화, 확장 포인트를 넣지 않는다.
- **신규 테스트와 기존 테스트가 모두 통과**하는지 전체 실행으로 확인한다.
- 테스트를 약화하거나 수정해서 통과시키지 않는다.

### REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **모든 테스트가 green인 상태를 유지**한다. 변경할 때마다 테스트를 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 반복

다음 동작에 대한 **RED로 돌아간다.** 요구된 모든 동작이 테스트로 덮일 때까지 반복한다.

## 3. 삭제 강제 규칙

**테스트보다 프로덕션 코드를 먼저 작성했다면, 그 코드를 삭제하고 RED부터 재시작한다.**

- "참고용"으로 남겨두는 것도 금지다. 주석 처리, 다른 파일로 옮기기, 복사해 두기 모두 포함한다.
- 삭제한 코드를 보고 다시 쓰지 않는다. 테스트가 이끄는 설계로 새로 작성한다.

## 4. 변명 차단표

| 변명 | 반론 |
| --- | --- |
| "너무 단순해서 테스트가 불필요하다" | 단순한 코드는 테스트도 단순하다. 비용이 거의 없고, 단순해 보이는 코드가 가장 흔히 회귀한다. |
| "나중에 테스트를 추가하겠다" | 나중에 쓴 테스트는 구현을 따라 쓰게 되어 이미 통과한다. 실패를 본 적 없는 테스트는 아무것도 증명하지 못한다. |
| "시간이 없다" | 디버깅과 회귀 수정이 테스트 작성보다 오래 걸린다. 급할수록 안전망이 필요하다. |
| "삭제하면 낭비다" | 매몰 비용이다. 검증되지 않은 코드를 유지하는 쪽이 더 비싸다. 다시 쓰는 데는 몇 분이면 된다. |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 버릴 코드라면 어차피 커밋하지 않는다. 남길 코드라면 테스트가 필요하다. |

## 5. 프로젝트별 규칙 우선

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선한다.**
- **이 파일은 기본값(fallback)이다.** 프로젝트 규칙이 없거나 침묵하는 부분에만 적용한다.
